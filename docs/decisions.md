## D1. 홈페이지 공지 목록·본문은 자동 수집하지 않는다

- **날짜**: 2026-11-10
- **배경**: 대전대학교 홈페이지 `robots.txt`가 게시판 목록·본문 경로(`/*/na/ntt/`)의 자동 수집을 제한한다. 사업단 홈페이지도 같은 도메인(`www.dju.ac.kr`) 아래에 있어 같은 규칙이 적용된다. 신청 기간과 마감일은 대부분 본문에 있어, 계획서대로 학교에 수집 허가를 요청하기로 했다.
- **진행**: 2026-11-10 SW중심대학사업단 담당 교수님께 수집 허가 절차를 문의했다.
- **회신 (같은 날)**: 학교 홈페이지 보안 사항이 민감하여, 학생 프로젝트를 위해 정책을 바꾸거나 사이트를 열어 두기는 어렵다는 답변을 받았다.
- **결정**: 공지 목록·본문 자동 수집은 이번 활동 기간에 추가하지 않는다. 계획서의 "허가를 받은 경우에만 추가한다"는 조건에 따른 결과다. 수집 범위는 계획서의 기본 범위(메인 페이지 최신 공지 칸의 제목·날짜·링크)로 유지한다.

## D2. 크롬 확장 프로그램을 추가한다

- **날짜**: 2026-11-17
- **배경**: D1 회신에서 교수님이 대안으로 "사용자가 직접 연 공지를 버튼으로 읽어 일정으로 등록하는 크롬 확장 프로그램"을 제안했다. 크롬의 `activeTab` 권한을 쓰면 사용자가 버튼을 누른 탭에만 접근할 수 있다.
- **결정**: 본문에 있는 마감일을 얻는 경로로 크롬 확장 프로그램을 만든다. 자동 수집이 아니라 **사용자가 이미 연 페이지**를 사용자가 요청할 때만 읽는다.
- **지킬 선**
  - 공지 목록을 돌며 글을 자동으로 여는 기능은 만들지 않는다. (그러면 다시 자동 수집이 된다.)
  - 버튼을 누를 때만, 지금 열려 있는 탭 하나만 읽는다.
  - 원문 전체는 저장하지 않고 정리한 항목과 원문 링크만 남긴다.
- **남은 한계**: 사용자가 연 공지를 버튼으로 등록하는 방식도 학교 이용 기준에서 허용되는지는 별도 확인이 필요하다. 이 한계는 [`collection-policy.md`](collection-policy.md)와 결과 발표에 그대로 밝힌다.

## D3. 인스타그램은 자동 수집하지 않고 프롬프트 방식으로 처리한다

- **날짜**: 2026-11-17
- **배경**: 공식 API(Business Discovery)를 쓰려면 팀 인스타그램 프로페셔널 계정, 연결된 페이스북 페이지, Meta 개발자 앱, 액세스 토큰(약 60일마다 갱신)이 필요하다. 남은 활동 기간(11.17 ~ 11.30) 안에 준비부터 자동 수집까지 마치기 어렵고, 팀 외부 학생이 레포만 보고 같은 설정을 따라 하기도 어렵다(세부 목표 "외부 학생 5명 설치 성공"과 충돌).
- **결정**: 인스타그램 자동 수집은 이번 활동 기간에서 제외한다. 인스타그램 게시물은 사용자가 캡션이나 포스터 캡처를 AI에 넣는 **프롬프트 방식**으로 정리한다. 같은 추출 프롬프트를 쓰므로 정리 결과 형식은 같다.
- **영향**: 계획서의 세부 목표 "대전대학교 공식 인스타그램과 사업단 채널 대상 자동화 완성" 중 인스타그램 자동 수집은 달성하지 못한다. 공식 API 연동은 향후 확장 계획으로 남긴다.

## D5. 목표 지표의 측정 방법을 바뀐 구조에 맞춘다

- **날짜**: 2026-11-17
- **마감일 정확도 90%**: 정의는 그대로다([`schema.md`](schema.md)). 크롬 확장·프롬프트 방식·자동화가 **같은 추출 프롬프트**를 쓰므로, 실제 공지 30건의 본문(+포스터)으로 한 번 측정한 값이 세 경로를 대표한다.
- **외부 학생 5명 설치 성공**: 계획서의 "레포 안내만으로 자기 캘린더 자동화 구현"을 아래처럼 확인한다.
  - 기본: 크롬 확장을 설치하고 API 키를 넣은 뒤, 공지 1건을 자기 구글 캘린더에 등록하면 성공
  - 심화: 레포를 fork하고 매일 자동 실행(GitHub Actions)까지 켜면 성공

## D6. 선택 기능(디스코드 알림)은 이번 기간에 만들지 않는다

- **날짜**: 2026-11-27
- **배경**: 계획서에서 새 공지 알림은 "기본 이메일, 사용자가 원하면 디스코드"로 적었다. 기본 기능(이메일)을 먼저 완성했다.
- **결정**: 남은 기간에는 필수 기능과 목표 지표(정확도 30건, 외부 학생 5명 설치)를 우선하고, 디스코드 알림은 향후 확장 계획으로 남긴다. `src/magami/notify.py`에 발송 함수를 하나 더 붙이는 구조라 나중에 추가하기 쉽다.

## D7. main 보호 규칙을 강화한다

- **날짜**: 2026-11-27
- **배경**: 계획서의 "모든 코드와 문서는 PR로 제출하고 다른 팀원 1명 이상의 검토를 거친 후 반영"을 레포 설정으로 강제한다.
- **결정**: main 규칙(Ruleset)에 다음을 적용한다. 예외 대상(bypass)은 없다.
  - PR 필수, 승인 1명 이상 (작성자 본인 승인은 인정되지 않음)
  - 승인 뒤 새 커밋이 올라오면 승인 취소, 마지막 push는 push한 사람이 아닌 팀원이 승인
  - 리뷰 대화가 모두 해결돼야 머지, 강제 push·삭제 금지
  - Squash 머지 끔 (팀원별 커밋 기록 보존)
  - 모든 PR이 머지된 뒤 "테스트 통과 필수"(`.github/workflows/test.yml`) 추가 예정
- **변경 (2026-11-28)**: "승인 뒤 새 커밋이 올라오면 승인 취소"를 끈다.
  - 이 옵션은 main이 바뀌어 PR의 기준점(merge-base)이 달라질 때도 승인을 취소한다. 앞 PR 위에 쌓아 만든 PR(#10 ~ #22)은 앞 PR이 머지될 때마다 승인이 다시 취소됐다. (#10은 같은 날 승인 4번이 모두 취소됨)
  - "마지막 push는 push한 사람이 아닌 팀원이 승인"은 그대로 둔다. 승인 뒤 작성자가 커밋을 더 올리면 다시 승인을 받아야 하는 점은 같다.
